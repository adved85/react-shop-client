---===== ADMIN AUTH & ROUTE PROTECTION =====---
@@@@ React Context + React Router — Step-by-Step Guide @@@@


OVERVIEW
--------
This guide documents how the admin area is protected: a shared AdminContext
holds the logged-in admin, a RequireAdmin wrapper guards private routes, and
a generic context helper gives clear runtime errors when a hook is used
outside its provider.

The chain used in this project:

    Login  →  AdminContext (state)  →  RequireAdmin (guard)  →  Protected route


-------------------------------------------------------------------
STEP 0 — REACT CONTEXT IN ONE MINUTE
-------------------------------------------------------------------

Normally data flows DOWN through props. If App holds the logged-in admin and
Sidebar — six levels down — needs it, you would have to thread it through
every component in between ("prop drilling"), and each of them takes a prop
it does not care about.

Context opens a side CHANNEL past all that:

    const ThingContext = createContext(null);   // 1. create the channel

    <ThingContext.Provider value={something}>   // 2. publish a value on it
        <App />
    </ThingContext.Provider>

    const thing = useContext(ThingContext);     // 3. read it, at any depth

Four things to keep in mind:

  Channel, not storage
      Context TRANSPORTS a value. The state itself still lives in a useState
      inside the provider component.

  Nearest provider wins
      A consumer reads the closest Provider above it IN THE RENDERED TREE —
      not the nearest one in the file.

  No provider = the default, silently
      With no Provider above it, useContext returns whatever you passed to
      createContext(...) — here null. It does NOT throw. That silence causes
      most context bugs, and STEP 2 exists to break it.

  Changing `value` re-renders consumers
      That is what makes context usable as shared state.

HOOK — a function whose name starts with "use" that plugs into React's
per-component state machinery (useState, useContext, ...). The prefix is not
a style rule: it is how React and its lint plugins recognise a function as a
hook, so they can enforce that hooks are only called at the top level of a
component or of another hook — never inside a condition, a loop, or a plain
helper function. useAdmin and useSafeContext below are CUSTOM HOOKS:
ordinary functions that call other hooks, named use* so the machinery can
see them.


-------------------------------------------------------------------
STEP 1 — THE PROBLEM
-------------------------------------------------------------------

Two bugs made RequireAdmin fail silently / redirect forever:

  1. AdminContextProvider was never mounted in App.jsx, so
     useContext(AdminContext) always resolved to the default value (null)
     and the helper below threw.
  2. Login.jsx saved the admin to localStorage directly but never updated
     the context state, so RequireAdmin never found out the user had
     logged in.

Both are fixed below.


-------------------------------------------------------------------
STEP 2 — GENERIC CONTEXT HELPER
-------------------------------------------------------------------

One helper is shared by every context hook (useAdmin, useTheme, ...).
It throws a SPECIFIC error naming both the hook and the provider, instead
of a generic message.

> src/components/context/contextHelpers.js

    import { useContext } from "react";

    export function useSafeContext(ctx, hookName, providerName) {
        const context = useContext(ctx);
        if (!context) {
            throw new Error(`${hookName} must be used within a ${providerName}`);
        }
        return context;
    }

Each hook passes its own name + provider name:

    export function useAdmin() {
        return useSafeContext(AdminContext, "useAdmin", "AdminContextProvider");
    }

  Why this matters:
    - Without it, forgetting to mount a provider fails with a vague error
      (or a crash further down the tree) instead of pointing straight at
      the missing provider.


-------------------------------------------------------------------
STEP 3 — ADMIN CONTEXT + PROVIDER
-------------------------------------------------------------------

Holds the logged-in admin and exposes login / logout. Persists across
reloads via localStorage.

  ❗CHANGED SINCE THIS LAYER WAS WRITTEN
    These three exports originally lived in one AdminContext.jsx. The lint
    pass split them in two, because a file exporting both a component and a
    non-component breaks Fast Refresh (react-refresh/only-export-components).
    The code is otherwise unchanged, and
    import { useAdmin } from "../context/AdminContext"
    still resolves — the path is the same, only the extension changed.

> src/components/context/AdminContext.js        (the context and its hook)

    import { createContext } from "react";
    import { useSafeContext } from "./contextHelpers";

    export const AdminContext = createContext(null);

    export function useAdmin() {
        return useSafeContext(AdminContext, "useAdmin", "AdminContextProvider");
    }

> src/components/context/AdminContextProvider.jsx    (the provider component)

    import { useState } from "react";
    import { AdminContext } from "./AdminContext";

    export const AdminContextProvider = ({ children }) => {
        const adminStorage = localStorage.getItem("adminStorage");
        const [admin, setAdmin] = useState(adminStorage ? JSON.parse(adminStorage) : null);

        const login = (admin) => {
            setAdmin(admin);
        };
        const logout = () => {
            localStorage.removeItem("adminStorage");
            setAdmin(null);
        };

        return (
            <AdminContext.Provider value={{ admin, login, logout }}>
                {children}
            </AdminContext.Provider>
        );
    };

  Why read localStorage in the initialiser:
    React state dies on refresh; localStorage survives it. Hydrating the
    initial state from storage is what keeps you logged in when you
    hard-reload the dashboard — otherwise `admin` would start as null on
    every page load and the guard would bounce you to login.

  Key point:
    localStorage.getItem always returns a STRING, so it must be
    JSON.parse'd before going into state — otherwise `admin` is a truthy
    string forever and logout / re-render checks behave oddly.


-------------------------------------------------------------------
STEP 4 — ROUTE GUARD
-------------------------------------------------------------------

Reads `admin` from context; redirects to login if there isn't one.

> src/components/context/RequireAdmin.jsx

    import { Navigate } from "react-router-dom";
    import { useAdmin } from "./AdminContext";

    export const RequireAdmin = ({ children }) => {
        const { admin } = useAdmin();

        if (!admin) {
            return <Navigate to="/admin/login" />;
        }

        return children;
    };

A component that renders its children CONDITIONALLY. Not logged in → it
renders a <Navigate> instead, which React Router treats as a redirect. That
is the entire protection mechanism.

  ⚠ THIS IS UI PROTECTION, NOT SECURITY
    The guard runs in the browser, where anyone can edit the JavaScript. It
    hides the admin screens; it does NOT protect data. The real protection is
    the API rejecting any request without a valid Sanctum token (see guide
    3). Never treat RequireAdmin as an authorisation boundary.

This only works if AdminContextProvider is an ANCESTOR of wherever
RequireAdmin is rendered — see next step.


-------------------------------------------------------------------
STEP 5 — REGISTERING THE PROVIDER
-------------------------------------------------------------------

AdminContextProvider wraps the router so every route (not just the
protected ones) can call useAdmin() if needed, and so RequireAdmin has a
provider to read from.

> src/App.jsx

    import { AdminContextProvider } from './components/context/AdminContextProvider';
    import { RequireAdmin } from './components/context/RequireAdmin';

    function App() {
      return (
        <AdminContextProvider>
          <BrowserRouter>
            <Routes>
              {/* ...public routes... */}

              <Route path="admin/login" element={<Login />} />

              <Route
                path="admin/dashboard"
                element={
                  <RequireAdmin>
                    <Dashboard />
                  </RequireAdmin>
                }
              />
            </Routes>
          </BrowserRouter>
        </AdminContextProvider>
      );
    }

  ❗THE ROUTE SHAPE CHANGED LATER
    This flat admin/dashboard route is what THIS layer built. The next layer
    replaced it with a nested /admin parent route whose children render
    inside an <Outlet>, so the sidebar and page shell render once — see
    guide 5, Step 3, for the current shape. What matters here is unchanged:
    the guard wraps the protected element.

  Why admin/login sits OUTSIDE the guard:
    If the login route were wrapped in RequireAdmin too, a logged-out visitor
    would be redirected to /admin/login, which would itself be guarded, which
    would redirect again — an infinite loop. The page that lets you BECOME
    authenticated can never require authentication.

  Rule of thumb:
    A context provider must sit ABOVE every component (guard, page, or
    hook) that consumes it in the tree.


-------------------------------------------------------------------
STEP 6 — SYNCING LOGIN WITH CONTEXT
-------------------------------------------------------------------

Login.jsx must update BOTH localStorage (for persistence across reloads)
AND the context (for the current render tree to know immediately).

> src/components/admin/Login.jsx

    import { useAdmin } from "../context/AdminContext";

    const Login = () => {
        const navigate = useNavigate();
        const { login: setAdminSession } = useAdmin();

        const handleLogin = async (data) => {
            const resposeData = await login(data);
            const { token, user: { email, name, id, system_role } } = resposeData;

            const adminData = { token, email, name, id, system_role };

            localStorage.setItem("adminStorage", JSON.stringify(adminData));
            setAdminSession(adminData);   // <-- updates AdminContext state
            navigate("/admin/dashboard");
        };
        // ...
    };

  Both writes are needed, because they cover different timescales:

    localStorage.setItem(...)  answers "am I still logged in AFTER A
                               REFRESH?" — survives the page, but React
                               never watches it
    setAdminSession(...)       answers "am I logged in RIGHT NOW?" —
                               re-renders every consumer immediately, but
                               dies on refresh

Without the setAdminSession(adminData) call, `admin` in context stays
null even after a successful login, and RequireAdmin bounces the user
straight back.


-------------------------------------------------------------------
STEP 7 — SAME PATTERN FOR OTHER CONTEXTS
-------------------------------------------------------------------

ThemeContext reuses the exact same useSafeContext helper, so it gets the
same clear error message for free:

> src/components/context/ThemeContext.js

    export function useTheme() {
        return useSafeContext(ThemeContext, "useTheme", "ThemeProvider");
    }

Any future context (CartContext, UserContext, ...) should follow this
pattern:

    1. XContext.js  — createContext(null) plus a use* hook calling
                      useSafeContext(Context, "useX", "XProvider")
    2. XProvider.jsx — the provider component owning the state
    3. Mount the provider ABOVE every consumer in App.jsx

  WHY THE SPLIT — react-refresh/only-export-components

    Fast Refresh is the Vite dev-server feature that swaps an edited
    component into the running page WHILE KEEPING YOUR APPLICATION STATE.
    Change a colour in the dashboard and you keep your logged-in session;
    you do not get bounced back to the login screen.

    It can only do that when it knows a file contains NOTHING BUT
    COMPONENTS. If a file also exports a context object or a hook, React has
    no safe way to hot-swap it — those values may be held by other modules —
    so it gives up and does a FULL PAGE RELOAD. That reload wipes the very
    state you were testing.

    Hence the rule, and hence the layout:

      XContext.js     the context object + the use* hook
                      .js — no JSX, no components
      XProvider.jsx   the provider component only
                      .jsx — components only

    A useful side effect: the extension now tells you what is inside before
    you open the file.
