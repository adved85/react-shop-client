# Admin Dashboard Navigation & Auth Hardening
### Sidebar, Content Components, Nested Routes, Token Fix & Server-Side Logout

---

## Overview

This guide documents five changes made together to turn the admin area from a single
static `Dashboard` page into a real multi-section dashboard, and to close two auth gaps
found while wiring it up:

1. **Sidebar** now links to real admin sub-routes and has its own styles.
2. A **`content/` directory** holds one component per sidebar item, swapped in via routing.
3. **Nested routing** under `/admin` renders the right content component through an `<Outlet>`.
4. **`api/client.js`** was reading the auth token from the wrong `localStorage` key, and had
   no reaction to a `401 Unauthorized` response.
5. **`AdminContext.logout()`** only cleared local state — the Sanctum token stayed valid on
   the server after "logging out".

**The chain used in this project:**

```
Sidebar (Link)  →  /admin/:section route  →  Outlet in Dashboard.jsx  →  *Content component
```

---

## Step 1 — Sidebar Navigation + Styles

`Sidebar.jsx` moved from `<a href="">` placeholders to real `react-router-dom` `<Link>`s,
one per admin section, plus a dedicated `.sidebar` style block.

**`src/components/common/Sidebar.jsx`**
```jsx
import React from "react";
import { useAdmin } from "../context/AdminContext";
import { Link, useNavigate } from "react-router-dom";

const Sidebar = () => {

    const { logout } = useAdmin();
    const navigate = useNavigate();

    const handleLogout = async (e) => {
        e.preventDefault();
        await logout();
        navigate("/admin/login");
    }

    return (
        <div className="card shadow sidebar mb-5">
            <div className="card-body p-5">
                <ul>
                    <li><Link to="/admin/dashboard">Dashboard</Link></li>
                    <li><Link to="/admin/categories">Categories</Link></li>
                    <li><Link to="/admin/brands">Brands</Link></li>
                    <li><Link to="/admin/brands">Products</Link></li>
                    <li><Link to="/admin/brands">Orders</Link></li>
                    <li><Link to="/admin/brands">Users</Link></li>
                    <li><Link to="/admin/brands">Shipping</Link></li>
                    <li><Link to="/admin/brands">Change Password</Link></li>
                    <li><a href="#" onClick={handleLogout}>Logout</a></li>
                </ul>
            </div>
        </div>
    )
}

export default Sidebar
```

> **Known follow-up:** Products / Orders / Users / Shipping / Change Password all currently
> point at `/admin/brands` — placeholders left until those routes + content components exist.
> Update each `Link` `to=` prop as its section is built.

**`src/assets/css/styles.scss`**
```scss
.sidebar {
    ul {
        li {
            border-bottom: 1px solid rgb(47 72 88 / 20%);
            margin-bottom: 2px;
            a {
                display: block;
                padding: 10px 10px;
                color: $primary-black;
                &:hover {
                    color: $primary-color;
                }
            }
        }
    }
}
```

**Why `handleLogout` and not `onClick={logout}` directly:**
- `href="#"` alone jumps the page to the top on click — `e.preventDefault()` stops that.
- `logout()` is now `async` (see Step 5) and does a server call before clearing local
  state, so the sidebar has to `await` it before navigating away.

## Step 2 — `content/` Directory: One Component Per Sidebar Item

Each sidebar item gets its own component, all living under a new `admin/content/`
directory. `Dashboard.jsx` itself no longer decides *what* to render — it only provides
the shared shell (title, sidebar, layout) and a slot for whichever content component the
current route maps to.

```
src/components/admin/content/
├── DashboardContent.jsx   ← stats cards for /admin and /admin/dashboard
└── CategoriesContent.jsx  ← placeholder for /admin/categories
```

**`src/components/admin/content/DashboardContent.jsx`**
```jsx
import React from "react";

const DashboardContent = () => {
    return (
        <div className="row">
            <div className="col-md-4">
                <div className="card shadow">
                    <div className="card-body">
                        <h2>1</h2>
                        <span>Users</span>
                    </div>
                    <div className="card-footer">
                        <a href="#">View Users</a>
                    </div>
                </div>
            </div>
            {/* ...Orders, Products cards... */}
        </div>
    )
}

export default DashboardContent
```

**`src/components/admin/content/CategoriesContent.jsx`**
```jsx
import React from 'react'

const CategoriesContent = () => {
  return (
    <div>
      <h3>CategoriesContent</h3>
    </div>
  )
}

export default CategoriesContent
```

**Convention going forward:** every new sidebar item (`Brands`, `Products`, `Orders`,
`Users`, `Shipping`, `Change Password`) gets its own `XContent.jsx` file in this same
directory, named after the section, exporting a single default component with no props —
routing (Step 3) is what decides which one is on screen.

## Step 3 — Nested Routing for `/admin` Sub-Routes

Previously `/admin/dashboard` was one flat, protected route rendering `Dashboard`
directly. Now `/admin` itself is the protected parent route, and each section is a
**child route** rendered inside `Dashboard` via `<Outlet>`.

**`src/App.jsx`**
```jsx
import Dashboard from './components/admin/Dashboard';
import DashboardContent from './components/admin/content/DashboardContent';
import CategoriesContent from './components/admin/content/CategoriesContent';
import { RequireAdmin } from './components/context/RequireAdmin';

// ...

<Route path="admin/login" element={<Login />} />

<Route path="/admin" element={
  <RequireAdmin>
    <Dashboard />
  </RequireAdmin>
}>
  <Route index element={<DashboardContent />} />
  <Route path="dashboard" element={<DashboardContent />} />
  <Route path="categories" element={<CategoriesContent />} />
</Route>
```

- `path="/admin"` renders `Dashboard` (wrapped in `RequireAdmin`) for **any** URL under
  `/admin`, regardless of whether a child route also matches.
- `<Route index .../>` matches `/admin` exactly (no further segment) — it's what fills the
  `<Outlet>` with `DashboardContent` on the bare `/admin` URL, instead of leaving it empty.
- `path="dashboard"` and `path="categories"` match `/admin/dashboard` and
  `/admin/categories` respectively, swapping in `DashboardContent` / `CategoriesContent`.

**`src/components/admin/Dashboard.jsx`**
```jsx
import React from "react";
import Layout from "../common/Layout";
import Sidebar from "../common/Sidebar";
import { Outlet } from "react-router-dom";

const Dashboard = () => {
  return (
    <Layout>
      <div className="container">
        <div className="row">
          <div className="d-flex justify-content-between mt-5 pb-3">
            <h4 className="h4 pb-0 mb-0">Dashboard</h4>
          </div>
          <div className="col-md-3">
            <Sidebar />
          </div>
          <div className="col-md-9">
            <Outlet/>
          </div>
        </div>
      </div>
    </Layout>
  )
}

export default Dashboard
```

**Key point:** `Dashboard` is now a **layout route** — it renders the sidebar and page
shell exactly once, and `<Outlet/>` is the placeholder React Router fills with whichever
child route's element matches the current URL. `Dashboard` never imports or names a
specific content component; adding a new section only means adding one `<Route>` in
`App.jsx` and one `Link` in `Sidebar.jsx`, no changes to `Dashboard.jsx` itself.

> Without the `index` route, visiting bare `/admin/` still renders the `Dashboard` shell
> (because it matches the parent path), but the `<Outlet>` has no matching child and stays
> empty — the stats cards would only show up at the longer `/admin/dashboard` URL.

## Step 4 — API Client Fixes: Correct Token Key + 401 Redirect

Two bugs in `src/api/client.js`:

1. The request interceptor read the auth token from a **`"token"`** key in `localStorage`
   that nothing ever wrote. `Login.jsx` actually stores it nested inside an
   **`"adminStorage"`** JSON blob (`{ token, email, name, id, system_role }`). Net effect:
   the `Authorization: Bearer …` header was never being sent on admin API calls.
2. The response interceptor had 401 handling stubbed out as comments
   (`// if (error.response?.status === 401) {}`) — an expired or invalid token just showed
   a toast and left the user stuck on a broken admin page instead of being sent back to login.

**`src/api/client.js`**
```js
import axios from "axios";
import { toast } from "react-toastify";
import { env, commonErrorCodes, retryErrorCodes } from "../config/env";
import { ENDPOINTS } from "./endpoints";

const MAX_RETRIES = 3;
const RETRY_DELAY = 1000;
const ADMIN_AUTH_ENDPOINTS = Object.values(ENDPOINTS.adminAuth);

function getAdminToken() {
    const adminStorage = localStorage.getItem("adminStorage");
    return adminStorage ? JSON.parse(adminStorage).token : null;
}

export const api = axios.create({
    baseURL: env.apiUrl,
    headers: { "Content-Type": "application/json" }
});

api.interceptors.request.use((config) => {
    const token = getAdminToken();
    if (token) {
        config.headers.Authorization = `Bearer ${token}`;
    }
    // ...
    return config;
});

api.interceptors.response.use(
    response => { /* ...unwraps response.data.data... */ },
    async (error) => {
        const { response, config } = error;

        if (!response) {
            toast.error("Network Error: Please, check your internet connection.");
            return Promise.reject(error);
        }

        if (response.status === 401 && !ADMIN_AUTH_ENDPOINTS.includes(config?.url)) {
            localStorage.removeItem("adminStorage");
            window.location.href = "/admin/login";
        }

        shouldRetrySpecificFailedRequests(error);

        if (commonErrorCodes.includes(response.status)) {
            toast.error(`Error ${response.status}: ${response.data.message}`);
        }

        return Promise.reject(error);
    }
);
```

**Why `ADMIN_AUTH_ENDPOINTS` is excluded from the redirect:** the Laravel API
(`laravel-shop-api`) returns `401` in two very different situations:
- **Wrong email/password** on `POST /admin/login` — the user is *already* on the login
  page; forcing a redirect there would just wipe the form and swallow the error message
  `Login.jsx` is trying to show.
- **Expired/invalid Sanctum token** on any *other* protected admin route (categories,
  brands, products, `/admin/logout` itself, …) — this is the case that should force a
  logout and send the user back to `/admin/login`.

`ADMIN_AUTH_ENDPOINTS` (`/admin/login`, `/admin/logout`, `/admin/register`) is the
exclusion list that tells the two cases apart, using `config.url` off the failed request.

**Confirmed against the backend** (`app/Http/Controllers/admin/AuthController.php`,
`app/Support/API/ApiResponse.php`):
- Successful login returns `{ success, message, code, data: { user, token } }` — the
  existing `extractNestedResponseData()` unwraps `response.data.data` to `{ user, token }`,
  which is what `Login.jsx` destructures and what `getAdminToken()` now reads back out.
- Wrong-credentials 401 returns `{ success: false, message: "Either email/password is
  incorrect", code: 401 }` (no `data` key) — has `.message`, so the existing toast works.
- An expired/invalid Sanctum token on a protected route (e.g. `auth:sanctum` on
  `/admin/logout`) falls through to Laravel's default `{"message": "Unauthenticated."}` —
  also has `.message`, and is exactly the case the new redirect logic targets.

## Step 5 — Logout Now Revokes the Server-Side Token Too

`AdminContext.logout()` previously only cleared `localStorage` and local React state — the
Sanctum token stayed valid on the server, so "logging out" was purely cosmetic on the client.

**`src/components/context/AdminContext.jsx`**
```jsx
import { createContext, useState } from "react";
import { getContext } from "./contextHelpers";
import { logout as logoutAdminApi } from "../../services/authAdmin.service";

export const AdminContext = createContext(null);

export const AdminContextProvider = ({ children }) => {
    const adminStorage = localStorage.getItem("adminStorage");
    const [admin, setAdmin] = useState(adminStorage ? JSON.parse(adminStorage) : null);

    const login = (admin) => {
        setAdmin(admin);
    };

    const logout = async () => {
        try {
            await logoutAdminApi();       // POST /admin/logout — revokes the Sanctum token
        } catch (error) {
            console.error("Logout request failed:", error);
        } finally {
            localStorage.removeItem("adminStorage");
            setAdmin(null);
        }
    };

    return (
        <AdminContext.Provider value={{ admin, login, logout }}>
            {children}
        </AdminContext.Provider>
    );
};

export function useAdmin() {
    return getContext(AdminContext, "useAdmin", "AdminContextProvider");
}
```

**Key point:** `logoutAdminApi()` is wrapped in `try / finally`, not `try / catch` alone —
local state and `localStorage` are cleared **whether or not** the server call succeeds
(e.g. the token was already expired and the call itself 401s). The user is never stuck
"logged in" client-side just because the revoke request failed; the worst case is a token
that's already unusable sitting server-side a little longer.

Because `logout()` is now `async`, every caller must `await` it — see `handleLogout` in
`Sidebar.jsx` (Step 1), which awaits `logout()` before calling `navigate("/admin/login")`.
