# Docker Image, CI & Releases
### Multi-stage Dockerfile + GitHub Actions + GHCR — Step-by-Step Guide

---

## Overview

This guide documents how the client becomes a production container image, and how that image reaches **GitHub Container Registry (GHCR)**.

Five pieces, added together:

| # | Piece | Purpose |
|---|-------|---------|
| 1 | `Dockerfile` | Multi-stage: Node builds the bundle, nginx serves it |
| 2 | `docker/nginx/default.conf` | SPA fallback, gzip, immutable asset caching |
| 3 | `.dockerignore` | Keeps everything the image does not need out of it |
| 4 | `.github/workflows/ci.yml` | Lint, test, Docker build + smoke test on every push/PR |
| 5 | `.github/workflows/docker-publish.yml` | Builds and pushes to GHCR on version tags only |

The end goal lives in another repository — **shop-infrastructure** holds one `compose.yml` that pulls this image alongside the API:

```yaml
services:
  nginx:      # edge reverse proxy / gateway
  frontend:
    image: ghcr.io/adved85/react-shop-client:${FRONTEND_VERSION}
  api:
    image: ghcr.io/adved85/laravel-shop-api:${API_VERSION}
  postgres:
  redis:
  rabbitmq:
```

This repo and [laravel-shop-api](https://github.com/adved85/laravel-shop-api) follow the **same pipeline shape**, so what you learn in one applies to the other:

```
ci.yml (fast checks)  ←── called by ──  docker-publish.yml (slow, tag-only)
```

> **Line-by-line reference:** this guide is the narrative. For directive-by-directive explanations of each file — plus a glossary of Actions/Docker/GHCR terms — see [docker_image_and_pipelines/](docker_image_and_pipelines/).

## Why the image contains its own nginx

A fair question: shop-infrastructure already runs an nginx service — why does this image run one too? Because they do different jobs:

| | Edge nginx (shop-infrastructure) | In-image nginx (this repo) |
|---|---|---|
| **Owns** | Port 443, TLS certificates | This app's static files |
| **Does** | Terminates HTTPS, routes by host/path | Serves files over plain HTTP :80 |
| **Scope** | One per fleet | One per frontend container |

Compare with the API: its image is **php-fpm only**, with no web server, because php-fpm speaks FastCGI and the edge nginx talks to it directly on port 9000. A static bundle has no such protocol — something must answer HTTP and hand back files — so this image brings the smallest thing that can.

> The alternative (ship only files, let the edge nginx serve them from a shared volume) was rejected: shop-infrastructure pulls this as an **image**, not a build context, so extracting files at compose time means volume tricks and an init container. Self-contained is simpler and, importantly, testable in CI on its own.

**Why not `serve` (the Node static server)?** It works, but it drags the whole Node runtime into the runtime stage for a job nginx does in ~20–40 MB, with better cache headers and gzip.

## Step 1 — The Production Dockerfile

**`Dockerfile`**
```dockerfile
# syntax=docker/dockerfile:1

# Keep in sync with .env's NODE_VERSION, which drives docker-compose.yml and CI.
ARG NODE_VERSION=25-alpine

########################################
# build: install dependencies and compile the Vite bundle
########################################
FROM node:${NODE_VERSION} AS build

WORKDIR /app

# Copied ahead of the source so this layer survives any change that does not
# touch the dependency set.
COPY package.json package-lock.json ./

RUN --mount=type=cache,target=/root/.npm npm ci

COPY . .

ARG VITE_API_URL
ENV VITE_API_URL=$VITE_API_URL

RUN npm run build

########################################
# runtime: static bundle served by nginx, fronted by a separate proxy service
########################################
FROM nginx:alpine AS runtime

COPY docker/nginx/default.conf /etc/nginx/conf.d/default.conf

COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

**Why two stages** — the final image contains *only* nginx plus the compiled bundle. Node, npm, `node_modules` and the whole source tree stay in the build stage and are thrown away. Nothing that built the app ships with it.

**Why `package.json` is copied before the source** — Docker caches per instruction. With the source copied first, every component edit would invalidate `npm ci` and reinstall everything. Copying only the manifests first means the install layer is reused until a dependency actually changes.

### ❗ The build-time env gotcha — the most important thing in this guide

Vite does **not** read environment variables at runtime. It **inlines** `VITE_*` values into the JavaScript at build time, as literal strings. Proof, from two builds of this exact Dockerfile:

```sh
# no build arg
$ grep -o 'apiUrl:[^,}]*' assets/index-*.js
apiUrl:``

# with --build-arg VITE_API_URL="https://laravel-shop-api.where/api"
$ grep -o 'apiUrl:[^,}]*' assets/index-*.js
apiUrl:`https://laravel-shop-api.where/api`
```

Consequences you must live with:

- An image is bound to **one** API URL. The same tag cannot be redeployed against a different backend without rebuilding.
- Setting `VITE_API_URL` in shop-infrastructure's compose file would do **nothing** — by then the value is already compiled in.
- The value comes from a build arg (fed by a GitHub repository variable, Step 6), not from a committed `.env.production`. That file is now gitignored.

> If one image ever has to serve several environments, the escape hatch is **runtime injection**: an entrypoint script that writes `env-config.js` into the web root from container env vars, read by the app at startup. Not done here — one environment, no need for the complexity.

> **Runtime user:** `nginx:alpine` starts its master as root and drops workers to the `nginx` user. For a fully non-root runtime, swap the base for `nginxinc/nginx-unprivileged:alpine` (listens on 8080).

## Step 2 — The nginx Config

**`docker/nginx/default.conf`**
```nginx
server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    gzip on;
    gzip_min_length 1024;
    gzip_types text/css text/javascript application/javascript application/json image/svg+xml;

    # Vite fingerprints these filenames, so a stale copy can never be served
    # for changed content.
    location /assets/ {
        add_header Cache-Control "public, immutable, max-age=31536000";
    }

    # Unknown paths belong to React Router, not to nginx — hand them index.html
    # instead of a 404 so deep links like /admin/dashboard work on hard reload.
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

**`try_files` — the line that makes a SPA work.** React Router handles `/admin/dashboard` in the *browser*. On a hard reload the browser asks the *server* for that path, and no such file exists on disk. Without `try_files`, nginx answers 404 and the app looks broken on refresh or on any shared deep link. `try_files` says: try the literal file, then the directory, then fall back to `index.html` and let the router sort it out.

**Why `/assets/` can be cached for a year.** `npm run build` writes fingerprinted filenames — `index-lDf1NLNW.js`. Change the code and the hash changes, so the URL changes. A cached copy can never be stale, because a stale URL is never requested again. `index.html` is *not* in `/assets/`, so it stays uncached and always points at the newest hashes.

> The `/assets/` block has no `try_files` of its own, so a genuinely missing asset still returns 404 rather than silently serving `index.html` — which is what you want, otherwise a broken script tag turns into an HTML file served as JavaScript.

## Step 3 — `.dockerignore`

```
node_modules
dist
.git
.gitignore
docker-compose.yml
.github
tests
.env
.env.development
.env.production
README.md
src/documentation
src/planing
```

Two reasons this matters:

- **Speed** — everything listed is skipped when the build context is sent to the daemon, and cannot invalidate a cached layer.
- **Correctness** — `COPY . .` would otherwise copy `.env` files into the build stage, where Vite would load them and silently outrank the build arg.

Verified — the final image contains only the built bundle:

```sh
$ docker run --rm --entrypoint sh react-shop-client:ci -c "ls /usr/share/nginx/html"
50x.html  assets  favicon.svg  icons.svg  index.html
```

## Step 4 — One Source for the Node Version

The Node version is written down **once**, in `.env`:

```
NODE_VERSION="25-alpine"
```

Consumed in three places:

| Consumer | How |
|----------|-----|
| `docker-compose.yml` (dev) | `image: node:${NODE_VERSION}` — Compose loads `.env` automatically |
| `Dockerfile` | `ARG NODE_VERSION=25-alpine` — the default is a fallback; CI passes the real value |
| `ci.yml` | A `setup` job greps the file and publishes it to the other jobs |

> ⚠️ **The value is needed in two shapes**, and this trips people up:
> - Docker wants the image tag: `25-alpine`
> - `actions/setup-node` wants a bare Node version: `25`
>
> `25-alpine` is a Docker Hub tag, not a Node release. Passing it to `setup-node` fails — GitHub runners are Ubuntu, there is no alpine flavor to download. The setup job derives both with shell parameter expansion:
>
> ```sh
> tag=$(grep '^NODE_VERSION=' .env | cut -d= -f2 | tr -d '"')
> echo "tag=${tag}"        >> "$GITHUB_OUTPUT"   # 25-alpine
> echo "version=${tag%-*}" >> "$GITHUB_OUTPUT"   # 25
> ```

## Step 5 — `ci.yml` (Fast Checks)

```yaml
name: React Vite CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

  # Lets docker-publish.yml gate a release on this exact pipeline instead of
  # redefining the checks there, which would let the two drift apart.
  workflow_call:
    outputs:
      node-tag:
        description: Node base image tag resolved from .env
        value: ${{ jobs.setup.outputs.node-tag }}

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

**The three triggers:** `push`/`pull_request` are the everyday signal on main and develop; `workflow_call` makes this whole file callable as one reusable unit from `docker-publish.yml` (Step 6).

**`concurrency`** — a second push to the same branch cancels the first run instead of queueing it. Saves minutes and stops stale results landing after fresh ones.

**Job graph:**

```
setup ──┬── lint          npm ci → npm run lint
        ├── test          npm ci → npm test      (vitest, see guide 6)
        └── docker-build  build the image, then smoke-test it
```

`lint`, `test` and `docker-build` run **in parallel** after `setup` — they do not depend on each other, and a lint error should not hide a broken Dockerfile.

**Why `docker-build` exists at all.** Without it, `docker-publish.yml` would be the first thing to ever build the image — meaning a broken Dockerfile is discovered while cutting a release. Building on every push moves that failure to the pull request.

The API repo does the same and then verifies php-fpm stays in the foreground. The equivalent check here is: *does nginx actually serve the bundle, and does the SPA fallback work?*

```yaml
- name: Verify nginx serves the built bundle and SPA routes
  run: |
    docker run -d --name smoke -p 8080:80 react-shop-client:ci
    ...
    curl -fsS http://localhost:8080/ | grep -q 'id="root"'

    # A deep link must fall through to index.html, otherwise React Router
    # routes 404 on hard reload.
    status=$(curl -s -o /dev/null -w '%{http_code}' http://localhost:8080/admin/dashboard)
    [ "$status" = "200" ] || exit 1
```

That second check is the one that would catch a deleted `try_files` line — a regression the app itself would not reveal until someone refreshed an admin page in production.

> This verification build passes `NODE_VERSION` but **not** `VITE_API_URL`, so the image it produces has an empty API URL (`apiUrl:``). That is deliberate — the job proves the image builds and serves, not that it talks to a backend. Only `docker-publish.yml` passes the real value.

> ⚠️ **Known state:** the `lint` job currently fails — 27 pre-existing ESLint errors in app code, unrelated to this layer (see [guide 6](6.testing-and-lint.md), Step 8). A separate "lint fixes" branch clears them.

## Step 6 — `docker-publish.yml` (Releases)

```yaml
name: Publish Docker image

on:
  push:
    tags:
      - "v*.*.*"
  workflow_dispatch:

permissions:
  contents: read
  packages: write

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}
```

**Why tags and not every push to main:** shop-infrastructure pins `${FRONTEND_VERSION}` to an exact version. Pinning only makes sense if versions are deliberate, human-chosen release points — not a floating tag that moves under the infra repo's feet.

**`permissions: packages: write`** is required for `GITHUB_TOKEN` to push to GHCR. Read access to the repo alone is not enough.

### The verify gate

```yaml
jobs:
  verify:
    name: Verify
    uses: ./.github/workflows/ci.yml

  build-and-push:
    needs: verify
```

A git tag can point at **any** commit, including one that never passed CI. `uses:` runs `ci.yml` as a reusable workflow, so a release re-runs the exact same lint, test and image-verification jobs — no copy of the test steps to drift out of sync.

Bonus: the image built during `verify` warms the shared Actions layer cache (`cache-from`/`cache-to: type=gha`), so the publishing build reuses those layers instead of starting from scratch. The Node version travels the same way — `ci.yml` declares `node-tag` as a `workflow_call` output, and the publish job reads it back:

```yaml
build-args: |
  NODE_VERSION=${{ needs.verify.outputs.node-tag }}
  VITE_API_URL=${{ vars.VITE_API_URL }}
```

### The `VITE_API_URL` repository variable

Because the URL is compiled in (Step 1), an unset variable would publish a release that talks to no API at all — and nothing would fail loudly. Hence the guard:

```yaml
- name: Require VITE_API_URL
  run: |
    if [ -z "${{ vars.VITE_API_URL }}" ]; then
      echo "Repository variable VITE_API_URL is not set."
      exit 1
    fi
```

Create it at **Settings → Secrets and variables → Actions → Variables → New repository variable**:

| Name | Value |
|------|-------|
| `VITE_API_URL` | `https://laravel-shop-api.where/api` |

> ❗ **Do not wrap the value in quotes.** In a `.env` file quotes are syntax and the parser strips them; a GitHub Actions variable is stored **literally**, so `"https://..."` compiles the quote characters *into* the string and every request goes to `https://.../api"/admin/login` and fails.

It is a **variable, not a secret**, on purpose: the value is visible in the shipped JavaScript anyway — a secret would only add false comfort.

### Image tags

```yaml
tags: |
  type=semver,pattern={{version}}
  type=semver,pattern={{major}}.{{minor}}
  type=sha,prefix=,enable=${{ github.event_name == 'workflow_dispatch' }}
```

Pushing tag `v1.2.3` publishes:

| Tag | Role |
|-----|------|
| `ghcr.io/adved85/react-shop-client:1.2.3` | Exact version — what the infra repo pins |
| `ghcr.io/adved85/react-shop-client:1.2` | Moving minor pointer |
| `ghcr.io/adved85/react-shop-client:latest` | Added automatically |

`latest` comes from `docker/metadata-action`'s default `latest=auto` flavor which — unlike an always-on latest tag — **skips pre-releases**. Tagging `v2.0.0-rc1` will not move `latest` off the current stable release. The `sha` tag only appears on manual `workflow_dispatch` runs, giving an unambiguous handle for a one-off build with no version behind it.

## Step 7 — Cutting a Release

```sh
git checkout main
git pull
git tag v0.1.0
git push origin v0.1.0
```

Then watch Actions: `verify` → `build-and-push`. When it finishes, the image appears under the repository's **Packages**.

> ⚠️ **First release only — package visibility.** A GHCR package is created **private**. shop-infrastructure will fail to pull it (`denied` / `manifest unknown`) until you either make the package public (Package settings → Change visibility), or log the pulling host in with `docker login ghcr.io -u <user> -p <PAT>` using a token carrying `read:packages`.

In shop-infrastructure's `compose.yml`:

```yaml
frontend:
  image: ghcr.io/adved85/react-shop-client:${FRONTEND_VERSION}
```

with `FRONTEND_VERSION=0.1.0` in that repo's `.env`. Deploying a new version there is a one-line change plus `docker compose pull && docker compose up -d`.

## Step 8 — Verifying Locally Before Pushing

Everything CI does can be run by hand:

```sh
# build exactly as the publish job does
docker build \
    --build-arg NODE_VERSION=25-alpine \
    --build-arg VITE_API_URL="https://laravel-shop-api.where/api" \
    -t react-shop-client:local .

# serve it (host port 8099 → container port 80)
docker run -d --name smoke -p 8099:80 react-shop-client:local

curl -fsS http://localhost:8099/ | grep 'id="root"'                       # index.html
curl -o /dev/null -w '%{http_code}\n' http://localhost:8099/admin/dashboard  # 200 = fallback OK
curl -o /dev/null -w '%{http_code}\n' http://localhost:8099/assets/nope.js   # 404 = correct

# what actually got baked in
docker run --rm --entrypoint sh react-shop-client:local \
    -c "grep -o 'apiUrl:[^,}]*' /usr/share/nginx/html/assets/*.js"

docker rm -f smoke
```

## File Structure Summary

```
.env                                   ← NODE_VERSION, the single source
.dockerignore                          ← keeps the build context lean
Dockerfile                             ← build (node) → runtime (nginx)
docker-compose.yml                     ← DEV ONLY, now reads ${NODE_VERSION}
docker/
└── nginx/
    └── default.conf                   ← SPA fallback, gzip, asset caching
.github/
└── workflows/
    ├── ci.yml                         ← setup → lint | test | docker-build
    └── docker-publish.yml             ← verify (calls ci.yml) → build & push
```
