---===== TESTING & LINT =====---
@@@@ Vitest + jsdom + ESLint — Step-by-Step Guide @@@@


OVERVIEW
--------
This guide documents the test setup added to the client: Vitest as the test
runner, jsdom as the browser environment, and a tests/ directory that mirrors
src/ instead of test files sitting next to the code.

What is covered by tests right now:

    src/api/client.js               — axios interceptors (auth header, response
                                      unwrapping, 401 handling, network errors)
    src/services/authAdmin.service.js — delegation to the API layer

What is deliberately NOT covered yet:
    React components and route guards. They need @testing-library/react and a
    render tree; the goal here was a working pipeline first, not coverage.

Why Vitest and not Jest:
    Vitest reads vite.config.js, so the tests run through the same transform
    pipeline (JSX, SVGR, aliases) as the app itself. Jest would need a second,
    parallel build config that could drift from Vite's.


-------------------------------------------------------------------
STEP 1 — INSTALL PACKAGES
-------------------------------------------------------------------

There is no Node.js on the host machine (see guide 1), so npm runs inside a
container:

    docker compose run --rm frontend sh
    npm install -D vitest jsdom

Or as a one-off, without the compose service:

    docker run --rm -u $(id -u):$(id -g) -e HOME=/tmp \
        -v "$PWD":/app -w /app node:25-alpine \
        sh -c "npm install -D vitest jsdom"

  vitest — the test runner.
  jsdom  — a browser-like environment (window, document, DOM APIs) so code
           that touches browser globals can run under Node.

> package.json

    "scripts": {
        "test": "vitest run"
    }

  `vitest run` runs once and exits — that is what CI needs. Plain `vitest`
  starts watch mode, which would hang a pipeline forever.


-------------------------------------------------------------------
STEP 2 — WIRE VITEST INTO vite.config.js
-------------------------------------------------------------------

> vite.config.js

    // vitest/config re-exports Vite's defineConfig and is what makes the
    // `test` block below take effect.
    import { defineConfig } from 'vitest/config'
    import react from '@vitejs/plugin-react'
    import svgr from 'vite-plugin-svgr'

    export default defineConfig({
      plugins: [react(), svgr()],
      server: { ... },
      test: {
        // Tests live outside src/ and mirror its layout:
        // tests/api/client.test.js covers src/api/client.js, and so on.
        include: ['tests/**/*.test.{js,jsx}'],
        // client.js reaches for localStorage and window.location.
        environment: 'jsdom',
        setupFiles: ['./tests/setup.js'],
      },
    })

  ❗IMPORTANT — the import line is not cosmetic:
    With `import { defineConfig } from 'vite'`, the `test` block is silently
    dropped: Vite does not know that key, so `environment: 'jsdom'` never
    applies and tests run in bare Node. The first symptom is a confusing
    failure like:

        TypeError: localStorage.clear is not a function

    Importing defineConfig from 'vitest/config' (it re-exports Vite's own)
    is what makes Vitest read the block.


-------------------------------------------------------------------
STEP 3 — THE localStorage SHIM
-------------------------------------------------------------------

Even with jsdom active, localStorage does not work out of the box on Node 25.
Node now ships its own built-in Web Storage global, and it shadows the Storage
implementation jsdom installs. Without --localstorage-file it is inert:
`localStorage` exists, but `localStorage.setItem` is undefined, and Node warns:

    Warning: `--localstorage-file` was provided without a valid path

The fix is a setup file that replaces the global with a working in-memory
Storage before any test runs. The app code stays untouched.

> tests/setup.js

    class MemoryStorage {
        #items = new Map()

        getItem(key)        { return this.#items.has(key) ? this.#items.get(key) : null }
        setItem(key, value) { this.#items.set(key, String(value)) }
        removeItem(key)     { this.#items.delete(key) }
        clear()             { this.#items.clear() }
    }

    Object.defineProperty(globalThis, 'localStorage', {
        value: new MemoryStorage(),
        writable: true,
        configurable: true,
    })

  Registered via `setupFiles: ['./tests/setup.js']` in vite.config.js, so it
  runs once per test file before the imports under test.


-------------------------------------------------------------------
STEP 4 — TEST LAYOUT
-------------------------------------------------------------------

Tests live in a top-level tests/ directory that mirrors src/:

    tests/
    ├── setup.js                           ← localStorage shim (Step 3)
    ├── api/
    │   └── client.test.js                 ← covers src/api/client.js
    └── services/
        └── authAdmin.service.test.js      ← covers src/services/authAdmin.service.js

  Why a separate directory instead of *.test.js next to the source:
    - src/ stays purely shippable app code; nothing test-only ends up in the
      production bundle's directory tree.
    - The whole directory is excluded from the Docker build context in one
      line of .dockerignore (see guide 7).
    - Where a test lives tells you what it covers: tests/api/client.test.js
      ↔ src/api/client.js.

  The cost: imports are relative to tests/, so they reach back into src/:

        import { api } from "../../src/api/client";


-------------------------------------------------------------------
STEP 5 — TESTING THE AXIOS INTERCEPTORS
-------------------------------------------------------------------

src/api/client.js exports a configured axios instance, and all the interesting
logic sits in its interceptors. Those handler functions can be pulled straight
off the instance and called directly — no HTTP server, no network mocking:

> tests/api/client.test.js

    import { toast } from "react-toastify";
    import { api } from "../../src/api/client";

    vi.mock("react-toastify", () => ({
        toast: { error: vi.fn() },
    }));

    const onRequest       = api.interceptors.request.handlers[0].fulfilled;
    const onResponse      = api.interceptors.response.handlers[0].fulfilled;
    const onResponseError = api.interceptors.response.handlers[0].rejected;

  What the 7 tests assert:

    request interceptor
      - Reads the token out of the "adminStorage" JSON blob Login.jsx writes
        and sends it as `Authorization: Bearer <token>`.
        (This is the exact bug fixed in guide 5, Step 4 — the interceptor used
        to read a "token" key nothing ever wrote.)
      - Sends no Authorization header when nobody is logged in.

    response interceptor (success)
      - Unwraps the API's nested { success, message, data: {...} } envelope.
      - Returns the body untouched when it is not nested.

    response interceptor (401)
      - On a protected route: clears adminStorage and redirects to
        /admin/login.
      - On /admin/login itself: does NOT clear or redirect, and shows the
        server's message as a toast — a wrong password must not wipe the form.
        (The ADMIN_AUTH_ENDPOINTS exclusion list from guide 5, Step 4.)

    network errors
      - No response object at all → "Network Error" toast.

  Two globals need stubbing:

    react-toastify — mocked with vi.mock so no real toast is rendered and the
      calls can be asserted.
    window.location — assigning to it for real would attempt a jsdom
      navigation, so each test installs a plain object first:

        Object.defineProperty(window, "location", {
            value: { href: "" },
            writable: true,
            configurable: true,
        });

  ⚠ Always pass a `config` object when calling the error handler. The retry
    helper does `Promise.reject(error)` when config is missing, and because it
    is called without await, that becomes an unhandled rejection that Vitest
    reports as a failure.


-------------------------------------------------------------------
STEP 6 — TESTING THE SERVICE LAYER
-------------------------------------------------------------------

The service layer is thin by design, so its tests mock the API module below it
and assert the wiring only:

> tests/services/authAdmin.service.test.js

    import * as adminAuthApi from "../../src/api/adminAuth";
    import { login, logout, register } from "../../src/services/authAdmin.service";

    vi.mock("../../src/api/adminAuth", () => ({
        login: vi.fn(),
        logout: vi.fn(),
        register: vi.fn(),
    }));

    it("passes credentials to the API and hands back the unwrapped session", async () => {
        const session = { token: "abc123", user: { id: 1, email: "admin@shop.test" } };
        adminAuthApi.login.mockResolvedValue(session);

        const result = await login({ email: "admin@shop.test", password: "secret" });

        expect(adminAuthApi.login).toHaveBeenCalledWith({
            email: "admin@shop.test", password: "secret",
        });
        expect(result).toEqual(session);
    });

  The 4 tests cover: credentials passed through and session returned, logout
  hitting the endpoint that revokes the Sanctum token, register forwarding its
  params, and failures propagating to the caller instead of being swallowed.

  Note: vi.mock is hoisted above the imports by Vitest, so the mock factory is
  in place before authAdmin.service.js pulls in its dependency — the order of
  the lines in the file is not the order they execute.


-------------------------------------------------------------------
STEP 7 — RUNNING THE TESTS
-------------------------------------------------------------------

Inside the dev container:

    docker compose run --rm frontend sh
    npm test

Or as a one-off:

    docker run --rm -u $(id -u):$(id -g) -e HOME=/tmp \
        -v "$PWD":/app -w /app node:25-alpine sh -c "npm test"

Expected output:

    ✓ tests/services/authAdmin.service.test.js (4 tests)
    ✓ tests/api/client.test.js (7 tests)

    Test Files  2 passed (2)
         Tests  11 passed (11)

Watch mode while developing (re-runs on save):

    npx vitest


-------------------------------------------------------------------
STEP 8 — LINT
-------------------------------------------------------------------

ESLint was already configured by the Vite scaffold (eslint.config.js, flat
config) and needed no changes for the tests — the test files import describe /
it / expect / vi explicitly from "vitest" rather than relying on Vitest's
`globals: true`, so no extra globals had to be declared.

    npm run lint

  ⚠ KNOWN STATE: `npm run lint` currently reports 27 errors in 20 files, all
    of them pre-existing app code, none from the test setup:

      22 × no-unused-vars                    — unused `React` imports (React 19
                                               does not need them with the new
                                               JSX transform)
       4 × react-refresh/only-export-components — context files exporting both a
                                               context/hook and a component
       1 × react-hooks/rules-of-hooks        — getContext() in contextHelpers.js
                                               calls useContext but is not named
                                               use*

    These are scheduled for a separate "lint fixes" branch. Until then the
    lint job in CI (guide 7) fails red — this is known, not a regression.
