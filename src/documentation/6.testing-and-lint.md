# Testing & Lint
### Vitest + jsdom + ESLint — Step-by-Step Guide

---

## Overview

This guide documents the test setup added to the client: **Vitest** as the test runner, **jsdom** as the browser environment, and a `tests/` directory that mirrors `src/` instead of test files sitting next to the code.

**Covered by tests today:**

| File under test | Tests | What they check |
|-----------------|-------|-----------------|
| `src/api/client.js` | 7 | Auth header, response unwrapping, 401 handling, network errors |
| `src/services/authAdmin.service.js` | 4 | Delegation to the API layer |

**Deliberately not covered yet:** React components and route guards. They need `@testing-library/react` and a render tree — the goal here was a working pipeline first, not coverage.

> **Why Vitest and not Jest?**
> Vitest reads `vite.config.js`, so tests run through the same transform pipeline (JSX, SVGR, aliases) as the app itself. Jest would need a second, parallel build config that could drift from Vite's.

---

## Step 1 — Install Packages

There is no Node.js on the host machine (see [guide 1](1.create-config.txt)), so npm runs inside a container:

```sh
docker compose run --rm frontend sh
npm install -D vitest jsdom
```

Or as a one-off, without the compose service:

```sh
docker run --rm -u $(id -u):$(id -g) -e HOME=/tmp \
    -v "$PWD":/app -w /app node:25-alpine \
    sh -c "npm install -D vitest jsdom"
```

| Package | Role |
|---------|------|
| `vitest` | The test runner |
| `jsdom` | Browser-like environment (`window`, `document`, DOM APIs) so browser code runs under Node |

**`package.json`**
```json
"scripts": {
    "test": "vitest run"
}
```

`vitest run` runs once and exits — that is what CI needs. Plain `vitest` starts watch mode, which would hang a pipeline forever.

## Step 2 — Wire Vitest into `vite.config.js`

**`vite.config.js`**
```js
// vitest/config re-exports Vite's defineConfig and is what makes the
// `test` block below take effect.
import { defineConfig } from 'vitest/config'
import react from '@vitejs/plugin-react'
import svgr from 'vite-plugin-svgr'

export default defineConfig({
  plugins: [react(), svgr()],
  server: { /* ... */ },
  test: {
    // Tests live outside src/ and mirror its layout:
    // tests/api/client.test.js covers src/api/client.js, and so on.
    include: ['tests/**/*.test.{js,jsx}'],
    // client.js reaches for localStorage and window.location.
    environment: 'jsdom',
    setupFiles: ['./tests/setup.js'],
  },
})
```

> ❗ **The import line is not cosmetic.**
> With `import { defineConfig } from 'vite'`, the `test` block is silently dropped — Vite does not know that key, so `environment: 'jsdom'` never applies and tests run in bare Node. The first symptom is a confusing failure:
> ```
> TypeError: localStorage.clear is not a function
> ```
> Importing `defineConfig` from `vitest/config` (it re-exports Vite's own) is what makes Vitest read the block.

## Step 3 — The `localStorage` Shim

Even with jsdom active, `localStorage` does **not** work out of the box on Node 25. Node now ships its own built-in Web Storage global, and it shadows the Storage implementation jsdom installs. Without `--localstorage-file` it is inert — `localStorage` exists, but `localStorage.setItem` is `undefined`, and Node warns:

```
Warning: `--localstorage-file` was provided without a valid path
```

The fix is a setup file that replaces the global with a working in-memory Storage before any test runs. **The app code stays untouched.**

**`tests/setup.js`**
```js
class MemoryStorage {
    #items = new Map()

    getItem(key)        { return this.#items.has(key) ? this.#items.get(key) : null }
    setItem(key, value) { this.#items.set(key, String(value)) }
    removeItem(key)     { this.#items.delete(key) }
    clear()             { this.#items.clear() }
}

Object.defineProperty(globalThis, 'localStorage', {
    value: new MemoryStorage(),
    writable: true,
    configurable: true,
})
```

Registered via `setupFiles` in `vite.config.js`, so it runs once per test file before the imports under test.

## Step 4 — Test Layout

```
tests/
├── setup.js                           ← localStorage shim (Step 3)
├── api/
│   └── client.test.js                 ← covers src/api/client.js
└── services/
    └── authAdmin.service.test.js      ← covers src/services/authAdmin.service.js
```

**Why a separate directory instead of `*.test.js` next to the source:**

- `src/` stays purely shippable app code; nothing test-only sits in the production tree.
- The whole directory is excluded from the Docker build context in one line of `.dockerignore` (see [guide 7](7.docker-ci-and-releases.md)).
- Where a test lives tells you what it covers: `tests/api/client.test.js` ↔ `src/api/client.js`.

The cost: imports reach back into `src/` — `import { api } from "../../src/api/client"`.

## Step 5 — Testing the Axios Interceptors

`src/api/client.js` exports a configured axios instance, and all the interesting logic sits in its interceptors. Those handler functions can be pulled straight off the instance and called directly — **no HTTP server, no network mocking**:

**`tests/api/client.test.js`**
```js
import { toast } from "react-toastify";
import { api } from "../../src/api/client";

vi.mock("react-toastify", () => ({
    toast: { error: vi.fn() },
}));

const onRequest       = api.interceptors.request.handlers[0].fulfilled;
const onResponse      = api.interceptors.response.handlers[0].fulfilled;
const onResponseError = api.interceptors.response.handlers[0].rejected;
```

**What the 7 tests assert:**

| Area | Assertion |
|------|-----------|
| Request | Reads the token from the `adminStorage` blob `Login.jsx` writes, sends `Authorization: Bearer <token>` |
| Request | No `Authorization` header when nobody is logged in |
| Response (success) | Unwraps the nested `{ success, message, data: {...} }` envelope |
| Response (success) | Returns the body untouched when it is not nested |
| 401 on protected route | Clears `adminStorage`, redirects to `/admin/login` |
| 401 on `/admin/login` | Does **not** clear or redirect; shows the server message as a toast |
| Network error | No response object → "Network Error" toast |

The first and the two 401 rows are regression tests for the exact bugs fixed in [guide 5](5.admin-dashboard-navigation-and-auth-hardening.md), Step 4: the interceptor used to read a `"token"` key nothing ever wrote, and a wrong password on the login page must not wipe the form.

**Two globals need stubbing.** `react-toastify` is mocked with `vi.mock` so no real toast renders and calls can be asserted; `window.location` gets a plain object, because assigning to the real one attempts a jsdom navigation:

```js
Object.defineProperty(window, "location", {
    value: { href: "" },
    writable: true,
    configurable: true,
});
```

> ⚠️ Always pass a `config` object when calling the error handler. The retry helper does `Promise.reject(error)` when `config` is missing, and because it is called without `await`, that becomes an unhandled rejection Vitest reports as a failure.

## Step 6 — Testing the Service Layer

The service layer is thin by design, so its tests mock the API module below it and assert the wiring only:

**`tests/services/authAdmin.service.test.js`**
```js
import * as adminAuthApi from "../../src/api/adminAuth";
import { login, logout, register } from "../../src/services/authAdmin.service";

vi.mock("../../src/api/adminAuth", () => ({
    login: vi.fn(),
    logout: vi.fn(),
    register: vi.fn(),
}));

it("passes credentials to the API and hands back the unwrapped session", async () => {
    const session = { token: "abc123", user: { id: 1, email: "admin@shop.test" } };
    adminAuthApi.login.mockResolvedValue(session);

    const result = await login({ email: "admin@shop.test", password: "secret" });

    expect(adminAuthApi.login).toHaveBeenCalledWith({
        email: "admin@shop.test", password: "secret",
    });
    expect(result).toEqual(session);
});
```

The 4 tests cover: credentials passed through and session returned, logout hitting the endpoint that revokes the Sanctum token, register forwarding its params, and failures propagating to the caller instead of being swallowed.

> `vi.mock` is **hoisted above the imports** by Vitest, so the mock factory is in place before `authAdmin.service.js` pulls in its dependency — the order of lines in the file is not the order they execute.

## Step 8 — Lint

ESLint was already configured by the Vite scaffold (`eslint.config.js`, flat config) and needed **no changes** for the tests — the test files import `describe` / `it` / `expect` / `vi` explicitly from `"vitest"` rather than relying on Vitest's `globals: true`, so no extra globals had to be declared.

```sh
npm run lint
```

> ⚠️ **Known state:** `npm run lint` currently reports **27 errors in 20 files**, all pre-existing app code, none from the test setup:
>
> | Count | Rule | Cause |
> |-------|------|-------|
> | 22 | `no-unused-vars` | Unused `React` imports (React 19 does not need them with the new JSX transform) |
> | 4 | `react-refresh/only-export-components` | Context files exporting both a context/hook and a component |
> | 1 | `react-hooks/rules-of-hooks` | `getContext()` in `contextHelpers.js` calls `useContext` but is not named `use*` |
>
> These are scheduled for a separate **"lint fixes"** branch. Until then the `lint` job in CI ([guide 7](7.docker-ci-and-releases.md)) fails red — known, not a regression.
